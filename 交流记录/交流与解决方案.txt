[H23] 2026-09-22（具体问答时间未在本档记录）｜better_fastlio2 与 FAST_LIO_SAM 比较
用户问题/需求：两个 GitHub 仓库能提供哪些回环/后端思路，哪个更适合本项目，哪个处理更快？
查询来源：https://github.com/Yixin-F/better_fastlio2 （读取版本 c188ce156237e3487b62ceac98b58da46a087e33）；https://github.com/kahowang/FAST_LIO_SAM （读取版本 757d1223cd8c97e70ab6d92c2e7299209a833fa2）。
代码事实：两者采用关键帧和 GTSAM/iSAM2。better_fastlio2 的在线回环先按位置半径寻找候选，再做 Scan Context 相似度校验和 ICP，并非直接全历史 Scan Context 检索；FAST_LIO_SAM 为距离候选和 ICP。二者都有向前端状态反馈和 ikd-Tree 重建相关代码。
环境：better_fastlio2 文档面向 Ubuntu 20.04/Noetic；FAST_LIO_SAM 文档面向 18.04/Melodic。better 的 CMake 即使不启用相机仍声明 darknet_ros_msgs 等依赖。
推荐方案：保留现有 FAST-LIO2 前端，参考两个仓库的关键帧/因子图实现，借鉴 better 的 Scan Context 校验；独立实现低频异步后端，结合静态关键帧地图和 map→odom。
性能结论：没有同硬件、同数据、同编译配置的对比测试，不能确认哪个更快。“FAST_LIO_SAM 更轻”和“裁剪 better 可接近其速度”均为结构上的估计。是否启动附加节点、ICP 点数、地图重建、磁盘保存和编译优化会显著影响结果。
补充限定：上轮的整机算力“基本足够”没有通过 CPU/Gazebo 并行负载测试；ldconfig 未发现 GTSAM 不等价于所有路径都没有安装；未 source 工作空间时 rospack 找不到包不能证明缺少依赖；Livox 支持也不等于 MID360 消息字段和时间戳已验证兼容。
拟议起点（非实测最优参数）：关键帧间隔约 1～1.5m 或 10～15°，回环检测约 0.5～1Hz，限制 ICP 子地图大小，再用相同 rosbag 测试精度、积压、延迟峰值和资源占用。
实际改动：无，未安装 GTSAM、未部署任一后端、未进行速度测试。
状态：仅完成调研与设计建议。坐标变换、回环约束可靠性、静态地图回写和控制连续性需要在实现时专项验证。
